## D. Required additions to v2 (founder-ruled; not in #37 as of 02f0e1f)

#37's six spec files contain no "launch" or "leadership", and its counter takes only `{changes, note}`.

### D1. Launch releases the plan to agents (RULED, LIM-2454 33ad545d, 2026-10-30)

Ruling:
- Approving a change request records the decision.
- Bound sessions get the new goal version only at launch.
- "Agreed, launch not yet" means the sessions are still on the previous version.

This extends the 10-22 one-wording ruling (LIM-2454 e3a14f87, open question 1). **Not in #37:** today one approval transaction creates the next goal version, sets `approved` and sends `goal_version` directives (specs/align/goals-and-proposals.md "Approving a change request"; lib/v2/goals.ts:454-499; lib/v2/changes.ts:217).

**State at 02f0e1f:** #37 now has goal holds (`hold`/`release` directives, directives.ts:16, register.ts:400) and typed requests, but approve still publishes at once (changes.ts:217 calls `writeGoalVersion`). The candidate mechanism, approve creating a held version and launch releasing it, waits on Sean (Monday #7). When he answers, this section will name the mechanism and add: held is not Stop in the UI and MCP reads, what an agent sees between approve and release, and who may release (#9).

- [ ] [API] **Split the approve transaction.** Approve records the decision (state `approved`, approver, note, revision) and holds the resulting version as approved-unlaunched. It writes no `goal_version` directive and doesn't move the published goal version agents read.
- [ ] [API] **Launch publishes.** A launch action publishes the held version through the single write path (`writeGoalVersion` or its successor) and writes the `goal_version` directives to every bound or governed session, in one transaction.
  - "Not yet" records the decision and publishes nothing.
  - A later call replaces the earlier one.
  - **Who may launch is OPEN** (Sean, Monday #9). v2 has no Leadership role, so don't invent a Leadership grant or role in UI, API or tests until it's ruled (LIM-2455 58d3c7a8). The route shape needs a v2 spec before code (Monday #7).
- [ ] [E2E] **Record wording.**
  - Before launch: "Approved, agents still on v<n> until launch".
  - After launch: "Launched, agents on v<n+1>".
  - Never show "agents on v<n+1>" before launch. Never imply agents executed anything: Align records delivery receipts, not execution.
- [ ] [API] **MCP and agent reads return the launched version only.**
  - `align_get_goal`, `align_list_goals`, `align_get_brief`, `align_get_decision_record`, `align_get_directives` and the goals feed (ETag) all return the last launched version, never the approved-unlaunched one.
  - An approved-unlaunched request shows as approved with `launch: not_yet` (or the spec's equivalent), declared in each tool's zod `outputSchema` (E).
- [ ] [API] **Acceptance test: approve without launching.**
  - Take a goal at v<n> with a bound session and a connected MCP client.
  - Approve a change request and don't launch. Assert:
    1. no new `goal_version` directive for the session (cursor unchanged);
    2. `align_get_goal` and the goals feed return v<n> content and an unchanged ETag;
    3. the record reads "Approved, agents still on v<n> until launch".
  - Then launch and assert: one directive carrying v<n+1>, MCP reads return v<n+1>, the ETag changes, and the record reads "Launched, agents on v<n+1>".
  - Repeat with "not yet" then launch, and with a rebase or `stale_version` between approve and launch.
- [ ] [MANUAL] **Still open, don't build until ruled:**
  - an "Approve and launch" one-step action when the approver may also launch (33ad545d);
  - what happens to an approved-unlaunched version when the owner saves a new version, or the goal is achieved or dropped before launch.

### D2. "Accept if…" conditions = requester acknowledgment (RULED, LIM-2454 35376283, 2026-10-30)

Ruling: a counter may carry a condition, and the requester acknowledges it is met. There is no independent "verified" state. **Not in #37:** v2's counter takes only `{changes, note}`, and `accept_counter` has nowhere to store a condition (lib/v2/changes.ts:233-253). Monday question #8 for Sean.

- [ ] [API] **Condition field.** A counter can carry condition text as its own field on the counter revision, separate from `note`. Length cap per the spec, e.g. TEXT_MAX 2000. Agents see it only as read-only data through the MCP reads below.
- [ ] [API] **Acknowledge action.**
  - Only the requester can acknowledge (403 `not_requester` otherwise), in one action that stores who acknowledged and when.
  - A second acknowledgement of the same revision returns 409.
  - The interaction with `accept_counter` (separate step or combined) is fixed in the spec.
  - Acknowledgment is **not** a gate on final approval or on launch unless the founder rules it one (LIM-2455 58d3c7a8). Final approval and launch stay separate steps. An unacknowledged condition stays visible as "Not confirmed yet" on the record and in MCP reads.
- [ ] [E2E] **Record.** The condition text and "Acknowledged by <name>, <time>" sit next to the approval. Before acknowledgement the condition reads "Not confirmed yet". No "verified" wording or state anywhere.
- [ ] [API] **MCP reads expose both.** `align_get_decision_record`, `align_list_change_requests` and `align_get_brief` return the condition text (wrapped as `untrusted_text`) and its acknowledgement status (`acknowledged_by`, `acknowledged_at`, or null). Every new field is declared in the zod `outputSchema` (E).
- [ ] [API] **Acceptance test.**
  - Counter with a condition. The requester accepts, and the condition shows as not acknowledged.
  - A non-requester acknowledges and gets 403.
  - The requester acknowledges; name and time are stored and returned by MCP.
  - Approve, then launch (D1). The record shows condition, acknowledgement and approval together.
- [ ] [MANUAL] Spec in `specs/align/` before any code.
