### Requirement: SQLite compatibility and public binding [authored:sqlite-schema-policy-v3]

# SQLite schema programs and JavaScript binding

This target Flavor owns the SQLite dialect and physical compatibility mapping for
`storage-schema.change-programs`. It selects SQLite schema semantics as a target
toolchain requirement, independently of the host OS and language Flavor. It does
not supply another compiler or replace the JavaScript command profile.

## Public binding

JavaScript module `storage_schema/change_programs` exports synchronous function
`change_programs()`. With no arguments it returns a fresh ordinary Array of
exactly 22 nonempty strings. Mutating a returned array must not alter a later
call. Corresponding strings are equal across invocations. The function performs
no database, process, filesystem, environment, clock, random or network access.
No npm dependency or runtime fixture is required. Importing this library does not
open a database or execute programs.

The strings are the SQLite change programs applied by the existing adapter. They
contain no BEGIN, COMMIT or ROLLBACK of their own and do not change connection
pragmas. They may change only the declared domain schema/data and the relevant
SQLite sequence state. They do not create, alter or delete external identity
tables, attach databases, inspect external files or configure a server.

## Physical mapping

The structured model below is normative for this target. Version 0 is empty of
domain entities. For each subsequent version, create the listed tables and apply
listed shape changes; append_columns extends the existing column order and other
keys replace that portion of the table description. The model describes required
states, not a program implementation or a replacement for data-preservation rules.
Perform the corresponding logical upgrade and preserve populated rows, values,
relationships and sequence high-water marks. Version 13 also performs the exact
approved-request backfill in the portable contract. Newly added optional fields
remain null; the declared defaults determine existing-row values for new fields.

Preserve physical names, column order and affinity, explicit non-null markers,
primary/unique key ordering, index names and collations, foreign-key field pairs
and introspection IDs, delete/update actions, partial-index predicates, rowid
allocation and event update guards. All tables are non-strict rowid tables with
immediate constraints and statement-level ABORT behavior. Add no conflict policy,
deferred constraint, generated column or extra check. Non-integer primary keys
gain no implicit NOT NULL. Nullable composite references and partial unique keys
retain SQLite's null behavior. Integer affinity remains SQLite affinity and must
not be replaced by strict typing.

Structured predicates use SQLite value, affinity and three-valued null semantics.
`and`, `or`, comparisons, `in` and inclusive `between` have their ordinary SQLite
meaning. `is_null` and `is_not_null` have their ordinary SQLite meaning. `length`
counts SQLite text code points. `json_valid` and `json_type` are SQLite's JSON
functions. A CHECK with a null result does not reject a row. The event update
guard aborts updates naming protected fields even when values are unchanged,
with message `v2_events is append-only`. Its privacy fields remain mutable.

SQLite's stored CREATE text is an implementation representation. Acceptance
compares its complete modeled semantics and metadata, data effects and behavior;
formatting and equivalent quoting are not serialized product output. Preserve
constraint error categories and the explicit event-guard message. Do not make
error-message SQL formatting a substitute for behavioral acceptance.

The original auth dependencies are external `ba_user.id` and `ba_passkey.id`.
Minimal test identities do not authorize an implementation of their full schema.
Consumer compatibility must pass on macOS Node 26.3.0 / SQLite 3.53.2 and Linux
Node 24.22.2 / SQLite 3.53.4. The library's pure string-producing interface uses
ordinary JavaScript; the application owns its actual SQLite driver and startup.

## Allocator preservation

Preserve the allocator row set as well as every stored high-water mark at each
historical version. A fresh empty domain store keeps an empty `sqlite_sequence`
row set through all 22 schema upgrades. Schema changes must not add zero-valued
allocator rows for empty audit, activity or directive tables. Existing allocation
rows retain their values, including gaps left by deleted rows. Rebuilding an
unrelated table must not create allocation history.
